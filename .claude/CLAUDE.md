# @rific/gestures

Standalone npm package (the `rific` npm org): shared gestures for React Native apps, so every swipe and pinch in the fleet feels the same. Started 2026-10-18 with `SwipeToDismiss`, lifted out of `@rific/toaster` (`../React-Native-Toaster`, 0.9.0) for Hangman's Pass & Play seats, with list rows the next obvious use. Pinch-to-zoom (`usePinchZoom`, `PinchZoomView`) came the same day, to replace six hand-rolled copies in three apps (see "Pinch to zoom" below).

**What belongs here** (Jay, 2026-10-18: "swipes and flicks and double taps and long presses"): a gesture earns a place once it carries real logic every app would otherwise rebuild, not as a thin wrapper over a gesture-handler one-liner. `Gesture.Tap().numberOfTaps(2)`, `Gesture.LongPress()` and `Gesture.Fling()` are one line each, so they come in only with something of their own (gated haptics, a leak-safe callback, a fleet-wide feel). Pinch-to-zoom qualified (focal-point zoom with clamping is fiddly math that drifted between six copies), so it's here: a hook handing back the gesture and its scale/translate shared values (a Skia board needs those, not a View) with a thin view over it. Options only for behavior at least two of those copies needed. `@tastic/input` is the games' layer of pure input math (swipe direction, aim, throw); layering runs @tastic on @rific, never the reverse, so math both want moves down into here.

npm run lint      # ESLint + Prettier check

npm test          # Run all Jest tests

```bash

```

The publish workflow fires on `v*` tags and runs `npm publish` with provenance (npm trusted publishing). A brand-new package has to exist on npm before trusted publishing can be set up for it, so its first version is published by hand.

## Architecture

| File | Purpose |
|---|---|
| `SwipeToDismiss.tsx` | The component: a stationary wrapper (the gesture's view, sized by `useOwnSize`) around an `Animated.View` that follows the finger. `buildSwipeGesture`, the pan's shared values (`useSwipeState`), the fly-out, the fade, `restore()`. |
| `swipe.ts` | The rules as tiny worklet functions, moved verbatim from the toaster: `swipeShouldDismiss` (past a fraction of the view's size, or a flick), `swipeIsVertical` (the axis lock), `swipeEdgeDrag` (resistance away from the edge), `sampleVelocity`/`releaseVelocity` (the flick speed), `swipeExitTarget` (1.5x the clearance, in the swipe's direction). Only the constants are public. |
| `usePinchZoom.ts` | The zoom hook: its shared values (`useZoomState`), `buildZoomGesture` (a Pinch and a Pan, `Gesture.Simultaneous`), the re-clamp when a size or bound changes, `reset()`. `usePinchZoomState` (internal) also hands back the web's `swallowClick` flag for PinchZoomView; `usePinchZoom` is the public face. |
| `PinchZoomView.tsx` | The thin view: a stationary viewport (the gesture's view, sized by `useOwnSize`, `overflow: 'hidden'`) around an `Animated.View` that fills it, centers the content and carries the transform. `reset()` through a `ref`. |
| `zoom.ts` | The zoom rules as tiny worklet functions: `zoomClampScale`, `zoomPinchScale` (the step from the pinch's change since its last event, bad scales skipped), `zoomAboutFocal` (the offset that keeps the point under the fingers under them), `zoomMaxOffset`/`zoomClampOffset` (the content covers the viewport, or stays centered while smaller). Only the constants are public. |
| `swallowClick.ts` | `useSwallowClick(ref, flag)`: the web's capture-phase `click` listener that stops the click after a drag (see SwipeToDismiss below). Shared by SwipeToDismiss and PinchZoomView. |
| `useOwnSize.ts` | `useOwnSize()` hands back `{ onLayout, ref, size }` for the stationary view: its size from `onLayout`, plus the web's measure two frames after mount if none has arrived (see "Its own size" below). Shared by SwipeToDismiss and PinchZoomView; internal. |
| `index.ts` | Public exports: `SwipeToDismiss`, `SwipeToDismissHandle`, `SwipeToDismissProps`, `SWIPE_ACTIVE_OFFSET`, `SWIPE_EXIT_MS` and the `swipe.ts` constants; `usePinchZoom`, `PinchZoom`, `PinchZoomOptions`, `PinchZoomView`, `PinchZoomViewProps`, `PinchZoomHandle` and the `zoom.ts` constants. |

### SwipeToDismiss

Everything the toaster learned carries over (see its CLAUDE.md, "Swipe-to-dismiss"): measured in the view's OWN coordinates (`x`/`y` minus where the pan activated, never the window-space `translationX/Y`), so it works inside a turned frame; the gesture on the STATIONARY wrapper, only the content inside it translated; the anchor taken at activation (`onStart`), not touch-down; `maxPointers(1)`; the flick speed sampled from local positions against `Date.now()`; the fly-out's completion signalled through a shared value and a `useAnimatedReaction` calling `@rific/core`'s `callWorkletCallback` by key (never `scheduleOnRN` of a component callback, which pins the component in memory). What's new here:

- **`edge` is optional.** The toaster always had one (its stack's). Without one the pan is sideways only: `activeOffsetX` and `failOffsetY` at `SWIPE_ACTIVE_OFFSET` (10pt), so a drag that goes up or down first fails and the scroll view around it keeps scrolling (the way gesture-handler's own Swipeable rows work in a list). On the web the detector also gets `touchAction='pan-y'`: gesture-handler's default `touch-action: none` on the wrapper would stop a phone's browser scrolling the page when a drag starts on the view (seen on Hangman's seats in the web preview, 2026-10-18). With an `edge` it stays `none`.
- **The swipe is on only while `onDismiss` is passed** (and after the first layout, since the thresholds are fractions of the view's size): `Gesture.Pan().enabled(...)`.
- **`restore()`** (a `ref`), for a dismissal the app declines: springs the content back and re-arms the swipe. Hangman's seats use it when a remove confirm is cancelled. It uses the shared values' `.set()`, which the React Compiler's lint rules accept.
- **Gone until restored:** once the fly-out starts (`gone`), a new touch on the empty wrapper is ignored (`tracking` false for that pan), rather than dragging the content back in from off-screen. The toaster unmounts a toast at once, so it never needed this; a confirm leaves the content mounted.
- **Its own size from its own layout** (`useOwnSize`), null until one with a width and a height arrives (no window-width guess). Until 0.1.2 a layout with a width and no height counted; since `useOwnSize` both components need both, which a view that can be touched always has.
- **A swipe is never also a press (web).** On native, gesture-handler cancels React Native's own touch handling once the pan activates. The web has no such step, and react-native-web presses on the browser's `click` at pointer-up, so a seat flicked away in Hangman's web preview was pressed (focused) on its way out. A pan that activates sets `swallowClick` (cleared at the next touch-down), and a capture-phase `click` listener on the wrapper's DOM node (`useSwallowClick`, in `swallowClick.ts` since PinchZoomView needs it too) stops that click before it reaches react-native-web's root listener. A plain tap never activates the pan, so it presses as before.
- **`touchAction`** on the detector (web): `pan-y` without an `edge`, so a phone's browser still scrolls up and down when a drag starts on the view; `none` with one.

Checked in Hangman's web preview (2026-10-18, 375x667): a real mouse flick removes a seat with the focus left where it was, a slow short drag springs back, and taps still focus a seat and open its picker. Not yet on a device: Fabric's pan inside a ScrollView (the sideways-only offsets), and a phone browser's `pan-y` scrolling.

### Pinch to zoom

Replaces six hand-rolled copies (read 2026-10-18): Utility's `PinchableImage` (a photo in a full-screen modal); Setter's wall screen (`src/app/(tabs)/walls/[id]/index.tsx`), its two route screens (`routes/create.tsx`, `routes/[routeId]/index.tsx`, the same code) and `HoldEditor` (the same wall, with a tap that adds or picks a hold); and Minesweeper's `MinesweeperBoardCanvas` (a Skia board with Pressable cells over it, transformed by a View style). All of them zoomed about the view's center (none followed the fingers), put the gesture on the very view they transformed, and panned by the window-space `translationX/Y`. Setter clamped the scale 1 to 5 and never the pan (the wall could be dragged off screen, even at 1x); Minesweeper clamped 0.5 to 3 and the pan to the board's edges (`maxOffset = max(0, (scaled - container) / 2)`) and waited for a 10pt drag so taps reached its cells; Utility added pinch scales instead of multiplying them, had no maximum, panned only while zoomed, and sprang back to 1x (and centered) when let go below it. None had a double tap, momentum or rubber-banding.

The model (`zoom.ts`'s header): the content is laid out centered in a stationary viewport, then moved by `translateX/Y` and scaled about its own center, which at rest is the viewport's, so React Native's `transform: [{ translateX }, { translateY }, { scale }]` applies it as is, and a Skia `Group` does with `origin` at the viewport's center. What every app now gets:

- **Zoom about the focal point, following the fingers.** Each pinch event first moves the content by the focal point's movement since the last event, then scales by the change in the pinch's own scale since the last event about the new focal point (`zoomAboutFocal`). So the pinch is also a two-finger pan, and what's under the fingers stays under them.
- **Every step is incremental**, from the change since the gesture's last event, never from where it started (Setter's and Minesweeper's `base * e.scale`). So the pinch and the pan can both be active, each adding its own movement, and turning a pinch around at a bound zooms back at once instead of first winding back the overshoot.
- **The pan stands aside while a pinch is active** (`pinching`), so two pinching fingers' movement counts once; it still pans with two fingers that aren't pinching (a pinch only activates once their distance changes), and with one.
- **Bounds after every step:** the scale between `minScale` and `maxScale` (`zoomPinchScale`), then the offset where the content still covers the viewport, or centered on an axis where it's smaller (`zoomClampOffset`). Fixed behavior, not an option: Setter's pan and Utility's unclamped pan lose the ability to drag the content off screen.
- **Measured in the viewport's own coordinates**, as SwipeToDismiss is: the pinch's `focalX/Y` and the pan's `x`/`y`, never `translationX/Y`, so it works inside a turned frame. That needs the gesture on a view that never moves, so PinchZoomView puts it on the stationary viewport and transforms only the content inside it, and the hook's docs tell a Skia board the same.
- **Anchored at activation, re-anchored when a finger lands or lifts.** Each gesture's last position (and the pinch's last scale) is taken at `onStart`, so nothing jumps by the touch slop or by the scale a pinch had already reached when it activated (iOS's pinch activates past a scale threshold). `x`/`y` and the focal point are every finger's centroid, so an event with a different `numberOfPointers` than the last only re-anchors.
- **A pinch scale that isn't a positive finite number is skipped** (Utility guarded for it), and the next good one is measured from the last good one.
- **The pan waits for `ZOOM_PAN_MIN_DISTANCE` (10pt)**, Minesweeper's `minDistance(10)`, so a tap or a long press on the content still reaches it.
- **The web's click after a pan or a pinch is swallowed** in PinchZoomView, as SwipeToDismiss does (Minesweeper's cells and Setter's holds are Pressables, and a drag released over one would otherwise press it on the web). The hook leaves it out: content that applies the transform itself (Skia) takes taps through gesture-handler, which the pan cancels.
- **A new size or bound re-clamps at once** (an effect, from the JS thread), and `reset()` eases scale, `translateX` and `translateY` back over `ZOOM_RESET_MS` (to `clamp(1, minScale, maxScale)`, centered).
- **Off until the viewport has a size** (`width`/`height` above 0), as SwipeToDismiss waits for its first layout.

Options are the ones at least two copies needed: `minScale`/`maxScale` (all six; the defaults, 1 and 5, are Setter's) and `contentWidth`/`contentHeight` (Setter's fitted wall four times, Minesweeper's board; Utility's photo fills the view, the default). Deliberately left out, each needed by one copy or none: Utility's spring back from below the minimum (the scale stops at the bound instead), Utility's pan only while zoomed (at 1x with content that fills the view the pan moves nothing anyway, though it still takes the touch: inside a pager or a scroll view this would want a pan that activates only while there's room to move, `manualActivation`), an `enabled` prop, double tap to zoom, momentum after a fling, rubber-banding, mouse-wheel zoom on the web, and a callback when the zoom changes. HoldEditor's tap stays the app's own: in a GestureDetector on the content inside PinchZoomView, where `e.x`/`e.y` stay in the image's own coordinates as now, and the zoom's pan activating should cancel it as `Gesture.Race` did (gesture-handler cancels the other gestures on the same touch; not yet checked on a device).

**Zoom only, no rotation (2026-10-18).** Jay pointed at Swirlio's twist, so a single transform hook (pinch, rotate and pan, each optional) was weighed and turned down. None of the six zoom copies rotate. The only copy that rotates content as a transform is HowBig's `useShapeTransform` (`src/hooks/useShapeTransform.ts`: pan plus a two-finger twist of a shape on a Skia canvas, about the shape's own center, unbounded, no pinch since the point is true size). That is moving an object, not zooming a viewport: it would flip every default (no pinch, no cover bounds, rotation on), and rotation breaks the cover bounds anyway (keeping a rotated rectangle over the viewport isn't a per-axis clamp). If a second object-manipulation copy turns up (a sticker or photo arranger), it earns its own hook: the same incremental step generalizes, translating with the focal point then rotating by the change in `rotation` and scaling about it (`t' = d + k * R(dTheta) * (t - d)`, `d` the focal point from the viewport's center, applied as `[translate, rotate, scale]`).

Surveyed at the same time and left out, none of them a view transform:
- **Swirlio's twist is its "Focus" control** (`src/app/index.tsx`, `rotationGesture`): `Gesture.Rotation` mapped per target onto a number, either a continuous scrub (`start + degrees * k`, clamped: stroke width, friction, hole radius) or a click-stop dial (`round(degrees / step)`, a haptic tick and a live commit per new step: mirror lines, bead count), plus Swirlio's own extras (a "bonus gear" past zero that flips alternate colors). Its pinch is the same shape over scale (`start + (scale - 1) * k`, five targets, a sticky zero for gravity), with a trackpad wheel standing in for the pinch on the web.
- **Pinch as a number elsewhere:** camera zoom in Utility's `CameraModal` and `CombinedCaptureModal` and in `@rific/scanner` (`baseZoom + (scale - 1) * 0.2`, clamped 0 to 1, a JS state update every frame, committed on end), and a column count in Utility's `debug/icons.tsx` and `useItemList` (one step on release past an 8% pinch).
- **Swirlio's spin** (`src/hooks/useEpicenter.ts`, `panGesture`): a one-finger drag around the pattern's center, split into its tangential part (rotation) and radial part (zoom, or color-cycle speed), with a dominant-axis snap, the angle delta wrapped across +-180, and a release that spins on at `omega = (r x v) / |r|^2`. Real math, but one copy.

A "two-finger knob" (a pinch or twist driving a number, continuous or in detents with a callback per step) is the candidate here: about ten mappings across Swirlio, Utility and the scanner. It would carry anchoring at activation (every copy measures from `scale - 1` or `rotation` as of touch-down, so the value likely jumps by the recognizer's slop when it activates; not checked on a device), bad-event guards, detent crossings with a leak-safe callback, and the live value kept on the UI thread with one commit on release. Each copy's own mapping is a line or two, though, so it isn't built: Jay's call. Swirlio's spin would join only with a second app that spins a dial by dragging around it.

PinchZoomView's viewport is the app's `style` plus `overflow: 'hidden'` (Setter's container clipped; Minesweeper's didn't, so its zoomed board could draw past the container); its content box fills the viewport absolutely and centers its children, so percentage sizes resolve against the viewport and the transform's origin is its center.

Not yet on a device (2026-10-18): it's only been run through the mocks. In particular the pinch and pan running together on Fabric, the order a pinch's and a pan's events arrive in (the math tolerates either), Android's pinch reporting `numberOfPointers`, and the web's two-finger pinch.

### Its own size

Both components size themselves from the stationary view's own layout and stay off until it has one, through `useOwnSize` (`{ onLayout, ref, size }`; the `ref` also goes to `useSwallowClick`). A layout counts once it has a width and a height above 0. On the web it also measures the node itself two animation frames after mount if no layout has arrived by then: `offsetWidth`/`offsetHeight`, the layout size react-native-web's own `getRect` reports to onLayout, which an ancestor's transform leaves alone (getBoundingClientRect would give a turned frame's rotated box, breaking the own-coordinates rule). A layout that arrives first cancels the frames; one that arrives later replaces the measured size. `Platform.OS`, not a `.web.ts` file: the web loads the one bundled `dist`, where a platform file can't be picked.

**What prompted it, and what it turned out to be (2026-10-19).** A browser check of 0.1.2 in Expo-Starter's demo (`/demos/gestures`, in the desktop app's built-in browser pane, hidden in the background) found no SwipeToDismiss row and no PinchZoomView sized on 3 of 4 loads, read as react-native-web losing the first onLayout through Expo Router, the race @tastic/core's `useSettledLayout` and @rific/scroll-view's ScrollViewProvider guard against. Looked at again before shipping a fix, it was the pane, not the package: a hidden pane sometimes has a 0x0 window (every view really is 0 wide, so there's no size to report) and sometimes draws no frames at all (no `requestAnimationFrame`, and so no ResizeObserver report, which comes with a frame). In both the nodes are fine (358 wide, the layout handler attached, connected), and the moment a frame is drawn (a screenshot of the pane did it) 0.1.2's onLayout sizes all six. In headless Chrome (`--headless=new`, which draws every frame, driven over the DevTools protocol), 0.1.2 sized every view through onLayout alone on 10 of 10 fresh loads of the demo and 6 of 6 client-side navigations into it from the home list (Expo Router's push), every one about 50ms after the views mounted (160ms once), the probe's polling interval. So nothing in a browser that draws needed the fallback.

It was kept as insurance (as the fleet's other two guards are), and checked live against a lost first layout made on purpose: a script run before the page dropped every element's first ResizeObserver report. 0.1.2 then never sized anything (3 fresh loads, 2 navigations), and a mouse drag and a two-finger touch pinch did nothing; with `useOwnSize` all six sized about 50ms after mounting on 10 of 10 (6 fresh loads, 4 navigations), a 240px mouse drag swiped the first row away, and the pinch zoomed the photo to 1.67x about its center. It can't help a pane that draws no frames (its frames don't come either), and doesn't need to: onLayout comes with the first frame. When a check in the built-in pane shows a view stuck unsized, look at `innerWidth` and whether `requestAnimationFrame` fires before blaming react-native-web.

## Hook callbacks say 'worklet' themselves

Every callback handed to a Reanimated hook (`useAnimatedStyle`, `useDerivedValue`, `useAnimatedReaction`, ...) starts with its own `'worklet'` directive. The worklets Babel plugin only spots a hook's callback by the hook's own name, and the web loads the bundled `dist` (Metro's web resolution doesn't take the `react-native` export condition), where tsup renames an import two files share: 0.1.1 shipped `useAnimatedStyle2` in SwipeToDismiss once PinchZoomView imported the hook too, so its style callback stayed a plain function and SwipeToDismiss threw on every web page (found through Expo-Starter's demo, 2026-10-19; native reads `src` and was fine). `hookWorklets.test.ts` compiles each source file with the real plugin as written and with every hook renamed the way the bundler did, and fails unless both make the same worklets. Gesture callbacks (`onStart`, `onUpdate`, ...) are spotted by method name, which bundling doesn't rename, but they carry the directive anyway.

## Testing

- Jest (`@infinitetoken/jest-config/react-native`, jsdom) + `@testing-library/react`. Mocks in `src/__mocks__/`, mapped in `jest.config.cjs`: `react-native` (a View records its `onLayout` in `lastOnLayout` and renders a div with its testID), `react-native-gesture-handler` (records the Pan's callbacks in `lastPanCallbacks` and its config in `lastPanConfig`, counts them in `panInstanceCount`; the Pinch's in `lastPinchCallbacks` and `lastPinchConfig`; `Gesture.Simultaneous` hands back `{ type: 'simultaneous', gestures }`; `lastDetectorProps` holds the detector's `gesture` and `touchAction`), `react-native-reanimated` (shared values that notify reactions on write, `withTiming` landing at once and reporting finished, `useAnimatedStyle` read live through a Proxy, the last one recorded in `lastAnimatedStyle`), `react-native-worklets`.
- `SwipeToDismiss.test.tsx` drives the pan's callbacks directly (a still clock for distance, a ticking one for flicks). The mock calls a disabled gesture's callbacks anyway, so a test of "no swipe" checks `lastPanConfig.enabled`, not a swipe.
- `useOwnSize.test.tsx` renders a probe View with the hook's `ref` and `onLayout`: animation frames are queued by a spy and run when a test says so, and the node's size is set as `offsetWidth`/`offsetHeight` own properties on the mock View's div (jsdom lays nothing out). It covers native (no frames, onLayout only), the web's measure at the second frame and not the first, a layout first (frames cancelled, the node never read), a later layout replacing the measure, an unsized node, and unmount. Each component's "on the web" tests add one case: sized from its node when no layout ever arrives.
- `usePinchZoom.test.tsx` drives the hook through `renderHook`, calling the pinch's and the pan's callbacks with viewport-relative positions and `numberOfPointers`; `PinchZoomView.test.tsx` covers the view (layout, its props, `reset()`, the web's click) and reads the transform off the content's `Animated.View`.
- `swipe.test.ts` and `zoom.test.ts` cover the rules; **`worklets.test.ts` runs them the way the UI thread does** (compiled with the Worklets Babel plugin, rebuilt from their code strings with only `this.__closure`). Never give a worklet a default parameter that names a module constant: it runs before the closure is unpacked and throws on the UI thread (the toaster's 0.8.0-0.8.2 release crash). A new rule in `swipe.ts` or `zoom.ts` needs calls in that test's `SWIPE_CALLS` or `ZOOM_CALLS`.
